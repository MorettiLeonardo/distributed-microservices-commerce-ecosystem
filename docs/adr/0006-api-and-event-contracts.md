# 0006 — API and event contracts

- **Status:** accepted
- **Date:** 2026-10-19

## Context and problem

Services communicate over HTTP and through events. Inconsistent contracts create coupling and hard-to-trace bugs.

## Considered options

- **Versioning:** URL; `Accept` header; no versioning
- **JSON casing:** camelCase; snake_case
- **Errors:** RFC 9457 Problem Details; custom format
- **Event envelope:** CloudEvents; custom envelope; native EventBridge format
- **Event naming:** reverse-DNS + version; PascalCase; short dot.case
- **IDs:** UUIDv7; ULID; prefixed IDs; auto-increment

## Decision

| Aspect | Choice |
|--------|--------|
| REST versioning | URL (`/v1/...`) |
| Casing | camelCase |
| HTTP errors | RFC 9457 (`application/problem+json`) with `code` and `correlationId` extensions |
| Event envelope | CloudEvents 1.0 (JSON) with `correlationid` extension |
| Event type | `com.ecommerce.<service>.<aggregate>.<fact>.v<N>` |
| IDs | UUIDv7 generated by the application |

## Consequences

- **+** Open standards (IETF, CNCF): interoperable and recognizable.
- **+** Version in the event `type` enables prefix filtering in EventBridge and contract evolution.
- **+** UUIDv7 is time-ordered (B-tree friendly) and needs no database round-trip to generate.
- **−** CloudEvents adds mandatory fields to the payload.
- **−** A breaking event change requires publishing two versions during migration.
