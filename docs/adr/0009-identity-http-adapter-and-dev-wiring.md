# 0009 — Identity HTTP adapter and development wiring

- **Status:** accepted; the in-memory/log stand-ins and the production guard superseded by [0010](0010-identity-real-adapters.md)
- **Date:** 2026-10-24

## Context and problem

The Identity domain and application layers were done, with no way to run the service. We had to choose the order in which adapters are built, how the service runs before Postgres/Redis/SQS adapters exist, how errors map to HTTP, and where the JWT signing key comes from.

## Considered options

- **Order:** real adapters one by one (persistence first); HTTP first wired to in-memory stand-ins.
- **Stand-ins:** everything fake; fake only what needs infrastructure.
- **Dev runner:** `tsx watch`; `tsc -w` + `node --watch dist`. Node's native type stripping is not an option: the code uses parameter properties, which are not erasable syntax.
- **HTTP tests:** native `fetch` against `listen(0)`; supertest.
- **bcrypt library:** `bcrypt` (native addon); `bcryptjs` (pure JS).
- **Signing key:** always from env; from env with an ephemeral fallback in development; always ephemeral.

## Decision

- **HTTP first.** In-memory/log stand-ins are used **only for what needs infrastructure**: repositories + `UnitOfWork` and `LoginAttemptLimiter` (in `src/adapters/out/in-memory/`, shared with the tests), `EventPublisher` and `EmailSender` (log only, `src/adapters/out/logging/`). Clock, UUIDv7, token generation, bcrypt and the ES256 JWT issuer are real.
- The composition root **refuses to start with `NODE_ENV=production`** while stand-ins are wired.
- New **`AccessTokenVerifier` port**, implemented together with the issuer by `JoseAccessTokens`; the HTTP adapter uses it for `GET /v1/users/me`.
- **Signing key always from env** (`JWT_PRIVATE_KEY`, P-256 private JWK), generated by `pnpm -s --filter @ecommerce/identity keys:generate`. `kid` = RFC 7638 thumbprint.
- **Error → HTTP status** mapped in one place (`problem-details.ts`) with a typed `Record<code, status>`. Request shape errors (Zod) ⇒ `400 VALIDATION_FAILED`; domain validation ⇒ `422`; bad credentials/tokens ⇒ `401`; rate limit ⇒ `429`; lockout ⇒ `423`; disabled user ⇒ `403`; invalid one-time tokens ⇒ `400`; unknown ⇒ `500` with no details.
- **Dev runner:** `tsx watch` (`pnpm --filter @ecommerce/identity dev`); production still runs `tsc` output.
- **HTTP tests:** native `fetch` against the real app on a random port.
- **bcrypt:** native `bcrypt`, its install script explicitly allowed in `pnpm-workspace.yaml`.
- **Logging now (minimal):** Pino + pino-http, `x-correlation-id` reused only when it matches `^[\w-]{1,64}$` (otherwise generated), sensitive fields redacted.

## Consequences

- **+** The service answers `curl` end to end, including real JWTs and JWKS.
- **+** Swapping a stand-in for a real adapter touches only `main.ts` — the hexagonal promise, made visible.
- **+** Tests and the running service share the same in-memory adapters (no duplication).
- **−** State is lost on restart; the in-memory limiter has no time windows (counters never reset).
- **−** The logging email sender writes one-time tokens to the log (development only), against the "never log secrets" rule, until the SQS adapter exists.
- **−** A new `DomainError` must be added to the mapped union, or it falls back to `500`.
- **−** `tsx` does not type-check; `pnpm typecheck` and the editor do.
